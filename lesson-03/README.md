# Домашнє завдання · Урок 3 (Поліморфізм і композиція, Go + GenAI)

Цей репозиторій — готовий каркас для домашньої роботи. Частина завдань
перевіряється **автоматично** через GitHub Actions при кожному пуші чи
Pull Request — запуште код у гілку `main` або відкрийте PR і перевірте
вкладку **Actions**.

**Загальний час на виконання:** ~2 години.

## Розділ 1 — Платіжна система з логуванням транзакцій (45 хв)

**Перевіряється автоматично тестами `payment/payment_test.go`.**

1. У файлі `payment/payment.go` вже задано `Transaction`, інтерфейс
   `PaymentMethod` і метод `LogInfo()` (готовий — просувається через
   вбудовування).
2. Додайте поля до `CreditCard` (`CardNumber string`, `Balance
   float64`) і `CryptoWallet` (`WalletAddress string`, `TokenBalance
   float64`) — обидві структури вже вбудовують `Transaction`.
3. Реалізуйте `Pay(amount float64) error` для обох типів:
   - недостатній баланс → поверніть помилку;
   - інакше відніміть `amount` від балансу і поверніть `nil`.
   - **приймач має бути вказівником** — метод змінює стан.
4. `ProcessPayment(method PaymentMethod, amount float64) error` уже
   реалізовано — вона викликає `Pay()` і виводить `LogInfo()`.

> 💡 Чому в `PaymentMethod` два методи (`Pay` і `LogInfo`), а не один?
> Оригінальне завдання просить `ProcessPayment` вивести просунуті
> поля `ID`/`Timestamp` — а функція, що приймає лише інтерфейс, не
> може «побачити» поля конкретного типу напряму. `LogInfo()`
> розв'язує це, залишаючись у дусі заняття: маленький інтерфейс,
> реалізований один раз на `Transaction` і автоматично просунутий на
> обидва типи.

Запустити тести локально:

```bash
go test ./payment/... -v -cover
```

## Розділ 3 — Використання ШІ-агента (45 хв)

### Крок 1 — Аналіз міксованих приймачів

**Перевіряється автоматично тестами `wallet/wallet_test.go`.**

У `wallet/wallet.go` — той самий код `SecureWallet`, що й у завданні,
з навмисною помилкою (міксовані приймачі). Запитайте ШІ-асистента:

> «Поясни, чому виклик `w.Deposit(50)` у циклі не оновлює оригінальний
> баланс у зрізі, хоча метод `Deposit` використовує pointer receiver.
> Яке золоте правило консистентності методів Go тут порушено і як це
> виправити?»

Потім реалізуйте `ApplyDeposits(wallets []SecureWallet, amt float64)`
так, щоб зміни справді зберігалися в оригінальних елементах (підказка
в коментарі коду — індексний `for`-цикл). За бажанням, для
консистентності методів, виправте й приймач `Balance()` на вказівник.

Запустити тести локально:

```bash
go test ./wallet/... -v -cover
```

## Що саме перевіряє CI (GitHub Actions)

Конвеєр `.github/workflows/tests.yml` на кожен push/PR виконує
повний чекліст ідіоматичного Go з цього заняття:

| Крок                                  | Що перевіряє                                                |
|----------------------------------------|--------------------------------------------------------------|
| Перевірка структури репозиторію        | Наявні всі обов'язкові файли                                  |
| Перевірка промпту (Розділ 2)           | TODO-заглушка в `prompts/...md` замінена на реальний текст   |
| Перевірка звіту (`REPORT.md`)          | Усі 4 TODO-заглушки замінені на реальний текст                |
| `gofmt -l .`                           | Код відформатовано за стандартом Go                           |
| `go vet ./...`                         | Немає підозрілих конструкцій                                   |
| `go test ./... -v -cover`              | Уся логіка проходить тести з покриттям                        |
| `go build ./...`                       | Проєкт компілюється без помилок                                 |

**Важливо:** усі кроки перевірки виконуються **незалежно один від
одного** — навіть якщо один крок провалився (наприклад, незаповнений
звіт), решта кроків (`gofmt`, `go vet`, тести, збірка) все одно
запускаються. Наприкінці окремий крок **«Підсумок перевірки»**
показує статус УСІХ перевірок одразу, а не лише першої помилки — щоб
ви бачили весь обсяг роботи, що залишився, за один погляд на лог.
